## 12.1 重入攻擊

重入（Reentrancy）是最經典、也最著名（The DAO，2016）的智能合約漏洞。當合約在**更新自身狀態之前**就向外部地址轉帳，惡意合約可在收款的 fallback 中「反過來再呼叫」原合約，在餘額尚未歸零時重複提款。

### 攻擊原理

```
受害合約 withdraw()               攻擊合約 fallback()
  │ 1. 檢查 balance[攻擊者] > 0
  │ 2. 送 ETH 給攻擊者 ──────────▶ 3. 收到 ETH，觸發 fallback
  │                                4. 再次呼叫 withdraw() ◀──┐
  │ 5. （尚未執行到）              （回到步驟 1，餘額還沒歸零）│
  │    balance[攻擊者] = 0           重複抽乾合約 ────────────┘
```

```solidity
// ❌ 有漏洞：先轉帳、後更新狀態
function withdraw() external {
    uint amount = balances[msg.sender];
    (bool ok, ) = msg.sender.call{value: amount}("");  // 外部呼叫 → 可重入
    require(ok);
    balances[msg.sender] = 0;                          // 太晚了！
}
```

用 Python 模擬攻擊如何抽乾資金：

```python
class VulnerableBank:
    def __init__(self):
        self.balances = {}
        self.pool = 0

    def deposit(self, who, amount):
        self.balances[who] = self.balances.get(who, 0) + amount
        self.pool += amount

    def withdraw(self, who, attacker=None):
        amount = self.balances.get(who, 0)
        if amount > 0:
            self.pool -= amount                    # 先把錢送出去
            if attacker:                           # 送款觸發攻擊者 fallback
                attacker.on_receive(self, who)     # ← 重入點
            self.balances[who] = 0                 # 後才歸零（太晚）

class Attacker:
    def __init__(self):
        self.depth = 0
    def on_receive(self, bank, who):
        if bank.pool > 0 and self.depth < 100:     # 只要池裡還有錢就再抽
            self.depth += 1
            bank.withdraw(who, attacker=self)

bank = VulnerableBank()
bank.deposit("victim", 100)
bank.deposit("attacker", 10)
atk = Attacker()
bank.withdraw("attacker", attacker=atk)
print(bank.pool)   # -100：合約被抽乾，連別人的錢一起被偷
```

### 防禦

**1. 檢查-生效-互動（Checks-Effects-Interactions, CEI）**——先改狀態，再做外部呼叫：

```solidity
function withdraw() external {
    uint amount = balances[msg.sender];
    balances[msg.sender] = 0;                          // ✅ 先歸零（Effects）
    (bool ok, ) = msg.sender.call{value: amount}("");  // 再互動（Interactions）
    require(ok);
}
```

**2. 重入鎖（ReentrancyGuard）**——用一個狀態旗標阻止函式被重入：

```solidity
modifier nonReentrant() {
    require(_status != ENTERED, "reentrant");
    _status = ENTERED;
    _;
    _status = NOT_ENTERED;
}
```

**3. 唯讀重入（read-only reentrancy）**——較新的變體：攻擊者不重入寫入函式，而是在重入期間讀取一個「暫時不一致」的 view 函式（如 AMM 的即時價格），欺騙**其他**依賴它的協議。防禦需擴大鎖的範圍，或讓外部協議避免在回呼期間讀取狀態。

## 12.2 常見漏洞模式

| 漏洞 | 說明 | SWC / 分類 | 防禦 |
|------|------|-----------|------|
| 整數溢位/下溢 | `uint` 溢位使餘額暴增 | SWC-101 | Solidity ≥0.8 內建檢查；或 SafeMath |
| 存取控制缺失 | 關鍵函式未加權限修飾 | SWC-105 | `onlyOwner`、角色管理 |
| tx.origin 認證 | 用 `tx.origin` 判身分可被釣魚 | SWC-115 | 一律用 `msg.sender` |
| delegatecall 注入 | 對不可信目標 delegatecall，儲存被劫持 | SWC-112 | 僅對可信固定目標使用 |
| 簽章重放 | 同一簽章被重複使用 | SWC-121 | nonce + chainId + domain separator（EIP-712） |
| 未檢查回傳值 | `call`/`send` 失敗被忽略 | SWC-104 | 檢查回傳布林或用 `call` + require |
| 拒絕服務（DoS） | 迴圈遍歷可膨脹陣列而耗盡 gas | SWC-128 | 改用 pull 模式、限制迴圈長度 |

**整數溢位**（0.8 前的經典）：

```solidity
// Solidity <0.8：uint8(255) + 1 == 0（回捲），可被用來繞過餘額檢查
uint8 x = 255;
x = x + 1;   // 0，無報錯
// Solidity ≥0.8：同樣運算會 revert（除非用 unchecked{}）
```

**tx.origin 釣魚**：

```solidity
// ❌ 若 owner 被誘導呼叫惡意合約，惡意合約再呼叫本函式，tx.origin 仍是 owner
require(tx.origin == owner);
// ✅ 應檢查直接呼叫者
require(msg.sender == owner);
```

**delegatecall 注入**：`delegatecall` 在**呼叫方的儲存空間**執行目標程式碼。若目標可被攻擊者控制、或儲存佈局不匹配，攻擊者可覆寫 owner 等關鍵變數——這正是 Parity 多簽事件的根源（見 12.7）。

## 12.3 經濟攻擊

有些攻擊不靠程式碼 bug，而是操縱**市場與協議的經濟假設**，程式碼「照規則執行」卻造成損失。

### 預言機操縱

若協議用某個 DEX 的**即時現貨價**當抵押品估值，攻擊者可用閃電貸瞬間扭曲該池價格，藉虛高抵押品超額借款：

```python
def spot_price(reserve_x, reserve_y):
    return reserve_y / reserve_x           # 現貨價：極易被單筆大交易扭曲

# 攻擊：向池砸入大量 X，瞬間推高 Y/X 報價 → 協議高估抵押品 → 超借
```

**防禦**：改用 **TWAP（時間加權平均價）** 或去中心化預言機（Chainlink），讓瞬間操縱成本極高（詳見 [章節08 預言機](章節08_DeFi核心協議實作.md)）。

### 閃電貸攻擊

閃電貸讓人在**單一交易內**無擔保借出巨額資金，只要同筆交易內還清即可。它本身是中性工具，但被用來放大其他漏洞（尤其預言機操縱）：

```python
def flash_loan_attack(pool, lending):
    borrowed = pool.flash_borrow(10_000_000)     # 1. 借出鉅款（無擔保）
    pool.swap_to_skew_price(borrowed)            # 2. 砸盤扭曲預言機價格
    inflated = lending.deposit_collateral(...)   # 3. 用被高估的抵押品
    stolen   = lending.borrow_max()              # 4. 超額借出真實資產
    pool.flash_repay(borrowed)                   # 5. 同筆交易還清閃電貸
    return stolen                                # 淨賺被盜資產
```

**三明治攻擊**是另一類經濟攻擊（在受害交易前後夾擊套利），屬於 MEV 範疇，詳見 [章節14 MEV](章節14_現代以太坊技術.md)。

## 12.4 安全開發模式

- **Pull over Push（提款模式）**：不要主動「推」錢給多個地址（任一失敗即整批卡住，且易被 DoS），改讓每個受款人自己「拉」——各自呼叫 `withdraw()` 領取自己的份額。
- **熔斷與速率限制**：對大額轉移設每日/每小時上限與 timelock，異常時可暫停（circuit breaker），為人工介入爭取時間。
- **代理升級模式的風險**：可升級合約用 `delegatecall` 把邏輯與儲存分離，但暗藏兩大坑——
  - **儲存槽碰撞（storage collision）**：新舊邏輯合約的變數佈局不一致，升級後讀寫錯位。用固定 slot（EIP-1967）規避。
  - **未初始化的實作合約**：實作合約若未鎖定 initializer，攻擊者可搶先初始化並奪權（Parity 事件）。用 `_disableInitializers()`。
- **治理防護**：關鍵參數變更走**多簽 + timelock**，讓社群有時間在惡意提案生效前反應（見 [章節10 治理](章節10_治理機制設計.md)）。

```solidity
// Pull 模式骨架
mapping(address => uint) public pending;
function claim() external {
    uint amt = pending[msg.sender];
    pending[msg.sender] = 0;                    // CEI：先歸零
    (bool ok,) = msg.sender.call{value: amt}("");
    require(ok);
}
```

## 12.5 審計與工具鏈

安全審計是分層防禦，工具與人工互補：

| 方法 | 代表工具 | 找什麼 | 特點 |
|------|---------|--------|------|
| 靜態分析 | Slither | 已知漏洞模式、危險呼叫 | 快、覆蓋廣、有誤報 |
| 模糊測試 | Echidna、Foundry `forge fuzz` | 違反不變量的隨機輸入 | 能找邏輯 bug，需寫好屬性 |
| 符號執行 | Mythril、Manticore | 探索所有路徑找可達的壞狀態 | 深入但可能路徑爆炸 |
| 人工審計 | 專業審計公司 | 業務邏輯、經濟假設漏洞 | 最貴但不可替代 |
| 漏洞賞金 | Immunefi 等平台 | 部署後的殘餘漏洞 | 持續、群眾外包 |

**審計流程**：需求/威脅建模 → 自動化掃描（CI 整合 Slither）→ 撰寫不變量並 fuzz → 人工審計 → 修復複審 → 部署後漏洞賞金與監控。**沒有任何單一環節足夠**；The DAO、Nomad 等事件多半是「該做的某一層沒做」。

```
# Foundry 不變量測試骨架（Python 偽碼表達其精神）
def invariant_total_supply_conserved(system):
    # 無論隨機執行多少操作，總供給恆等於各帳戶餘額之和
    assert system.total_supply == sum(system.balances.values())
```

## 12.6 形式化驗證

形式化驗證（Formal Verification）用**數學證明**合約在所有可能狀態下都滿足規格，而非像測試只抽樣有限輸入。核心是先寫下**不變量（invariant）**——任何時刻都必須成立的性質，再用工具證明它永遠不被違反。

| 方法 | 原理 | 工具 | 局限 |
|------|------|------|------|
| Model Checking | 窮舉狀態空間檢查性質 | Certora Prover | 狀態爆炸；需抽象化 |
| Theorem Proving | 以邏輯推導證明定理 | K Framework、Coq | 需人工撰寫證明、門檻高 |

```
// Certora CVL 規格風格（示意）
rule 轉帳不會憑空生成代幣 {
    uint before = totalSupply();
    transfer(to, amount);
    assert totalSupply() == before;   // 不變量：轉帳不改變總供給
}
```

**局限**：形式化驗證只能保證「合約符合你寫下的規格」——若**規格本身寫錯或不完整**（沒把某個經濟假設寫進去），依然會出事。它排除實作 bug，但無法保證你想的商業邏輯是對的。因此它是人工審計的補充而非替代。

歸納這些事件：損失最慘的往往不是艱深的密碼學缺陷，而是**基本功沒做好**——狀態更新順序、初始化、存取控制、經濟假設。跨鏈相關事件與 `BRIDGE_SECURITY_INCIDENTS` 交叉參見 [章節09 跨鏈安全](章節09_跨鏈互操作性.md)。

> **🔄 技術更新（2025+）**：**AI 輔助審計**（如用 LLM 掃描合約邏輯）與**即時監控/自動熔斷**（如 Forta、鏈上防火牆）正興起，能在攻擊交易被打包前偵測異常並暫停協議。同時**形式化驗證工具鏈**（Certora、Halmos 等）日益普及，頭部協議已將其納入 CI；帳戶抽象（[章節14](章節14_現代以太坊技術.md)）帶來的可程式化安全策略（交易模擬、支出限額）也成為錢包層新防線。
